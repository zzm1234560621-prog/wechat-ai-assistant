你在排查一个把 hook 注入微信进程的个人助手项目（工作目录就是项目根）。先读根目录的 `CLAUDE.md`，那里有 hook 铁律、两套 schema 差异和已知故障模式——**它是权威，不要凭一般经验另起炉灶**。

## 排查纪律（重要）

**你是在一个 700MB、且已被注入的微信进程上操作。你的每一个查询都可能把它拖死。**

- **不要裸调 `GetAllDBName`**，一次都不要。唯一允许的调用点是 `live_history.force_rescan()`。
- **不要发不带选择性过滤的排序查询**（如 `WHERE local_type=1 ORDER BY create_time DESC`）。
- **不要凭猜测批量试查询**。先用 `bot.log` 定位，再发**一条**有针对性的查询验证假设。
- 如果一条 `SELECT 1 FROM xxx LIMIT 1` 超过 1 秒才返回，说明卡的是微信进程本身，**立刻停手**并如实报告，不要再发第二条。
- 不要重启微信（会掉登录态）。也不要为了"清理干净"去杀进程——先问用户。

## 标准流程

1. **读 `bot.log` 尾部**，找轮询心跳 `[bot] 轮询心跳 #N，游标=X`。
   - 游标不动 + 无报错 → 极可能是 **fts 句柄静默失效**（本项目的头号坑）。
   - 有 `⚠️ 慢查询` → 记下那条 SQL，它就是要修的目标。
   - 有 `⚠️ 分片查询失败` → 看是哪几个分片。
2. **不要急着连真微信**。能靠日志和代码读出来的先读出来。
3. 需要验证时才发查询，且只发 `live_history.py` 里已有的查询路径，不要自己拼新 SQL。
4. 静默失效的恢复手段是 `live_history.force_rescan(client)`，**不需要重启 bot**。
5. 微信崩溃（minidump）→ 见下。

## 崩溃排查

历史崩溃都是 `0xC0000005` 访问违规、**读 NULL**，出错指令在 `Weixin.dll`，栈上有 `rowid`（说明在处理 DB 查询结果）。没有 PDB，符号化不了。

- **坑**：崩溃 dump 的模块列表里**看不到 hook 的 `version.dll`**（只有 system32 那个 45KB 的）。hook 是手动映射的，主动把自己从模块链表摘掉了。**别据此判定「hook 没加载」。**
- 先看崩溃前有没有**两个 bot 同时在轮询**（`bot.py` 已有单实例锁，占回环端口 39001；`netstat -ano | findstr 39001`）。
- 解析 minidump 的脚本在 `%TEMP%\md_parse.py` / `md_stack.py`（若还在）。
- 有链接器/系统环境问题就问用户；**不要**试图自己升级或替换 `version.dll`——编译产物和线上那个不是同一个二进制，换上去可能直接坏掉。

## 报告要求

- 给出**证据**（日志原文、SQL、耗时），不要给"可能是……"的猜测。
- 明确区分「已确认」和「推测」。
- 如果根因在 `live_history.py`，指出具体行号，并说明要动的是哪个函数。
- 修完提醒用户跑 `selftest_aixed.py`（假服务，不碰真 hook）。
