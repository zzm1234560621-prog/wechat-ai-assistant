| | 值 |

## 为什么不是更聪明的 glm-4.7-flash（它也免费）

两个独立的硬理由，都是实测出来的：

**① 限流严重。** 同一把 key、同一时刻，每个模型连打 6 次：

```
glm-4.7-flash       状态=[200, 429, 429, 429, 429, 200]   ← 4/6 失败
glm-4-flash-250414  状态=[200, 200, 200, 200, 200, 200]  ← 全绿
glm-4-flash         状态=[200, 200, 200, 200, 200, 200]  ← 全绿
```

429 的正文是 `{"error":{"code":"1305","message":"该模型当前访问量过大，请您稍后再试"}}`。
注意 **1305 = 模型被挤爆**，跟 **1308 = 额度用尽** 不是一回事（官方错误码表）。
**关掉思考也照样 429**，所以不是参数问题。

**② 默认开思考，会把输出预算吃光。** GLM-4.7 系列默认 `thinking: enabled`（官方「思考模式」页：
4.7 起默认开，不同于 4.6 的"自动"）。

```
同一句「介绍你自己」，max_tokens=2000：
  thinking=disabled → 0.76s  思考 0 token    正文正常
  thinking=默认(开) → 7.37s  思考 770 token  正文正常

max_tokens=64（短回复）：
  glm-4.7-flash → finish_reason=length，completion_tokens=64
                  reasoning_tokens=64，**正文是空字符串**
```

最后那条是这个项目最忌讳的**静默失效**：用户拿到一条空回复，日志里却是一次"成功"的调用。
`llm.py` 的 `truncated` 判据（`finish_reason == "length"`）能标出来，但正文已经没了。

## 三条通路的实测结果（都用真 key 打过）

| 模型 | 普通对话 | 工具调用 | 工具结果回传（第 2 轮） | 耗时 |
|---|---|---|---|---|
| `glm-4-flash-250414` | ✅ | ✅ | ✅ | 0.2~0.5s |
| `glm-4-flash` | ✅ | ✅ | ✅ | 0.4~1.7s |
| `glm-4.5-flash` | ✅ | ✅ | ✅ | ~1.4s（**官方定价表里没有这个型号**，别用） |
| `glm-4.7-flash` | ✅ | ✅ | ✅ | 0.9s（但 4/6 次 429） |
| `glm-4.6` / `glm-4.7` | ❌ `1113 余额不足` | | | 付费模型，本 key 没余额 |

第 2 轮是**故意不带 `reasoning_content`** 打的（官方「思考模式」页要求"交错思考 + 工具"时把它原样回传，
而 `llm.py` 现在不回传）。对 `glm-4-flash-250414` 没有影响——它本来就不思考。
**哪天换回 glm-4.7-flash 或别的思考模型，这条要重测。**

工具调用用的是一道中文选工具的题（3 个工具里选 `send_text`，并填对 `to` / `text`），
`glm-4-flash-250414` 直接给出 `{"to": "张三", "text": "会议改到下午三点"}`，参数正确。

## 还没做、但知道该做什么

- **`llm.py` 不重试**。免费模型是共享池，429 迟早会撞上，撞上就是把报错原文回给用户。
  要扛住得给 `_OpenAICompat._post` / `chat` 加**有界重试**（只重试 429/5xx，指数退避）。
  ⚠️ 这跟 CLAUDE.md 里「发送失败不重试」**不是同一条规矩**——那条说的是**发微信消息**
  （不可逆，重试可能发两条）；重试一次模型调用是安全的。
- **GLM 这几款都只收文本、不收图**。图片走 `image.mode=ocr`（系统 OCR）不受影响；
  但 `image.mode=inline`（原图直接给模型看）会失效。好消息：智谱的
  **`glm-4.6v-flash` / `glm-4v-flash` / `glm-4.1v-thinking-flash` 也是免费的**，
  想恢复"模型自己看图"可以配到 `image.vision` 那一段（注意 `glm-4v-flash` 上下文只有 4K）。
- 免费额度用尽时返回 **1308**，撞上它重试没用，得等下一个周期。

## 附：图片「视觉模型」也换成了智谱（2026-10-04 同日）

聊天模型是 **文本模型**（GLM-4.7/4-Flash 都只收文本），所以 `image.mode: inline` 走不通
（原图发过去服务端直接回 HTTP 400 不支持多模态）。于是把 `image.mode` 从 `ocr` 改成
**`vision`**，并把 `image.vision` 指向同家免费的视觉模型：

```yaml
image:
  mode: vision
  ocr_first: true        # 默认开，别关
  ocr_min_chars: 20
  vision:
    base_url: "https://open.bigmodel.cn/api/paas/v4"
    model: "glm-4v-flash"     # 免费
```

### 三个免费视觉模型的实测对比

用项目自己的 `image_read.vision()` 打的（不是裸 HTTP）：

| 模型 | 结果 | 结论 |
|---|---|---|
| **`glm-4v-flash`** | **8/8 成功**，0.67~2.1s；3000x2000 与 2.57MB 噪声图都吃得下；输出干净 | ✅ 用它 |
| `glm-4.6v-flash` | 2 次调用**撞 2 次 429**（code 1305） | ❌ 和 glm-4.7-flash 同一类限流问题 |
| `glm-4.1v-thinking-flash` | 能用，但**把 `<think>` 思考标签吐进正文**（4.87s / 3.62s） | ❌ 那段会被当成"图片描述"喂给聊天模型 |

⚠️ `glm-4v-flash` 上下文只有 **4K**（官方定价页），但实测 2.57MB 的图照样成功——
说明它内部会自己缩放，**不需要**我们预先缩图。

### `ocr_first` 闸门在实际图上的表现（重要）

`ocr_first: true` 时，vision 模式**先跑一遍系统 OCR**，抽出 ≥`ocr_min_chars`(20) 个字就直接用
OCR、**一次视觉模型都不调**。实测四张测试图 **OCR 全都没到 20 字**（图标/海报里只有零星几个字，
还带空格与乱码），所以都落到了视觉模型——而**视觉模型的结果明显更好**：

| 图 | 系统 OCR | 最终（视觉模型） |
|---|---|---|
| 照片1（海报） | 0 字 | 「你唱响 / 超级盟友 / 年情义…」 |
| 照片2 / 照片3（图标） | 5 字「战 略 版」 | 「三国志战略版」 |
| 照片5（广告） | 17 字含乱码「各 柙 杩」 | 「开年第一红 / 超大红包+各种好礼」 |

所以：**聊天截图那种大段文字**会被 OCR 接住（本地、不上传），**图标/海报/照片**才走视觉模型。
两边都免费。

### 两个已核实、但**没改代码**的事实

1. **`vision` 这条路不过 `image.send_max_bytes`、也不缩图**（`image_read.handoff` 的 vision 分支
   在缩图/上限代码之前就 return 了）。真正生效的体积闸是 `image.max_bytes`（聊天缩略图那条，
   默认 5MB）和「当文件发来的图」用的 `file.max_bytes`（默认 **0 = 不限**）。
   实测 2.57MB 没问题，所以这次没动代码；哪天有人发十几 MB 的原图再谈。
2. **`image.vision.api_key` 不复用顶部的聊天 api_key**（设计上允许视觉模型换别家，
   key 各管各的）——所以同一把智谱 key 要**填两处**，换 key 时两处都得改。

### 顺带确认：系统 OCR 在真机上是好的

在 DSH 沙箱里跑 `tools/ocr.ps1` 会报 `System.UnauthorizedAccessException`（WinRT 文件代理
不给受限进程访问权），**那是沙箱限制，不是真机故障**——用完整权限重跑就正常
（`ENGINE: zh-Hans-CN`）。**别被这个报错误导去改 ocr.ps1。**
另外该脚本 catch 时只打印外层 `AggregateException` 的消息、把真正的内层异常吞了，
排查时要么提高权限重跑、要么自己写诊断脚本 dump `InnerException` 链。
