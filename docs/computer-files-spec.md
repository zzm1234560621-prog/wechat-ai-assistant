# 电脑文件能力（`computer_files`）规格

> 状态：设计已与用户确认（2026-10-04）。
> **用户口径原话**：路径「用户可以设置，默认全盘」；触发者「只能说我的对话，加指定对话」；
> 确认「用户可以决定，默认读写不用，删要」；系统目录「可以跳过挡住」。
> **两处追加拍板（同日）**：① `overwrite`（覆盖已存在文件）单加一道闸；
> ② 把「发盘上任意路径的文件」一起打通（见 2.1，且有一条安全结论要知悉）。
> 本能力是 `docs/plugin-contract-spec.md` 那个扩展契约的**第一个消费者**
> —— 它落地同时就验证了那份契约装不装得下真的功能。

## 一、目标与非目标

**目标**：用户通过微信就能列目录 / 搜文件 / 读内容 / 写 / 建目录 / 复制 / 移动 / 重命名 /
删除（进回收站），以及**把盘上任意白名单路径的文件发给别人**。

**非目标（明确不做，别顺手扩）**：

- ❌ **不是 `run_command` 的第二条路**。本工具**只做文件操作，不执行任何程序**。
  `run_command` 依然是逃生通道，且**每条都要确认**（那条规矩一个字都不动）。
- ❌ **不做 UI 自动化**（模拟键鼠）。它会占住轮询线程（hook 不支持并发，操作期间收不了微信），
  界面一变就碎，失败了还很难如实报清「做到哪一步了」。
- ❌ **不写 MCP / IDE 连接器**（见插件规格第五节）。
- ❌ **不做永久删除**，也不做「清空回收站」。删除**只进回收站**，本轮不给关掉这个行为的选项。
- ❌ `write` / `append` **只接受文本**（那是解析后的内容）；`copy` / `move` / `rename`
  **不限文件类型**（那是搬字节，不解析内容）。

## 二、工具形状

**一个工具** `computer_files`，`action` 枚举 —— 照 `group` 工具的既有形状
（`action=status|add|remove|del|labels`），不新增 10 个工具名。

| 类别 | action | 参数 | 默认闸门 |
|---|---|---|---|
| 读 | `list` | `path`, `limit` | 免确认 |
| 读 | `find` | `path`(根), `name`(模式), `limit`, `depth` | 免确认 |
| 读 | `info` | `path` | 免确认 |
| 读 | `read` | `path`, `cursor` | 免确认 |
| 写 | `write` | `path`, `text`, `overwrite` | 免确认（**新建**）；**覆盖已存在文件要确认** |
| 写 | `append` | `path`, `text` | 免确认 |
| 写 | `mkdir` | `path` | 免确认 |
| 写 | `copy` | `src`, `dst` | 免确认 |
| 写 | `move` | `src`, `dst` | 免确认 |
| 写 | `rename` | `path`, `new_name` | 免确认 |
| 危险 | `delete` | `path` | **必须确认 + 进回收站** |

- **`read` 复用 `file_read.extract()`**（`file_read.py` 是「读文件的唯一入口」）：这样
  Office / PDF / 老 Office / 图片 / 音频 / 压缩包 / 邮件 / SQLite **全都自动可用**，
  本工具只是换了一套**准入策略**（哪些路径可读），抽取内核一个都不重写。
  → **一个抽取内核、两套门**，不是两个读文件的所有者。
- **`list` / `find` 必须有上限**（`limit` 默认 200，`find` 另有 `depth` 默认 3），
  超了**明说「还有多少没列」**——静默截断是本项目最忌讳的失效。
- **工具指导文本里要带上解析后的 `roots`**（如「你的桌面是 `C:\Users\x\Desktop`」），
  否则模型会去猜用户的目录名。

> ✅ **已定（用户 2026-10-04 拍板）**：`write` 覆盖一个**已存在的**文件是不可逆的，
> 所以 `write` **默认只新建**（目标已存在则如实拒绝并说明，不覆盖）；
> 要覆盖必须显式给 `overwrite=true`，而 **`overwrite` 默认进确认名单**（`files.confirm`）。
> 用户原话「读写不用确认」在**新建**这条路上照旧生效，不受影响。

### 2.1 发任意路径的文件（扩 `send_file`，用户 2026-10-04 拍板「一起来」）

`t_send_file` 的定位口径从「只认微信 `msg/file/`」放宽为
**「`msg/file/` ∪ `files.path_ok` 允许的任意路径」**：

| 来源 | 定位 | 准入 |
|---|---|---|
| 微信 `msg/file/` | `file_read.pick(name)`（**原样不动**） | 既有边界 |
| 盘上任意路径 | 绝对路径直接给 | 必须过 `files.path_ok` |

> ⚠️ **一条安全结论，请知悉（不是我自作主张，是清单内直发那条路必须有边界）**：
> `t_send_file` 对**`agent.auto_send_whitelist` 里的人直接发、不走确认**
> （`agent_tools.py:4491`）。今天这条路可以接受，是因为可达文件集被钉死在 `msg/file/`
> ——也就是**你自己在微信里收发过的东西**。
> 一旦放开成任意磁盘路径而**同时**保留直发，就等于：
> **模型能把盘上任意文件发给白名单里的人，一次确认都不要。**
> 诱因不必是恶意——它刚读完的那份文件、群里某人提到的一个文件名，都够。
>
> **所以：任意磁盘路径来源的文件，一律进确认队列，绝不走「名单内直发」。**
> 与 `delete` 永远强制确认同源（不可逆的外发动作不给配置留后门）。
> `msg/file/` 那条老路**一个字不动**（不回归）。
> 这一条也正好让代码符合 `t_send_file` 自己 docstring 里已经写的
> 「文件这一路**永远要用户回「确认」**才发」。

**确认菜单怎么显示**（这里有个既有规矩要照顾）：

- `describe_pending` 现在对 `kind == "file"` **只显示文件名**
  （`agent_tools.py:1904-1907`，理由是「全文路径里有本机目录，用户认的是文件名」），
  并且 `selftest_policy.py:228` 对图片有一条对应的断言
  「图片：不把完整路径塞进菜单」。**这条既有行为不改、既有测试不动。**
- 但**任意磁盘路径**上只有文件名是**不够的身份**：两份 `报告.pdf` 在确认菜单里长得一样，
  用户就是在**确认一个自己分辨不出的东西**（＝「重名不许静默取第一个」那条铁律在确认菜单上被违反）。
- **所以分级显示**：待确认项在 `extra` 里带来源标记
  —— `msg/file` 来源 → 只显示文件名（原样）；**磁盘路径来源 → 显示原样路径**
  （长则截断，**必须标注截断**）。
  两者不冲突：图片那条讲的是**从缓存里翻出来的**图（用户没给过路径、认的是文件名），
  而磁盘路径是**用户自己给的那条路径**，确认要审的就是它本身。

## 三、路径模型

- `files.roots: []` —— **空列表 = 全盘**（你的口径）。
- `files.deny: [...]` —— 默认挡系统关键目录（你的口径「系统目录可以跳过挡住」）：
  `C:\Windows`、`C:\Program Files`、`C:\Program Files (x86)`、`C:\ProgramData`。
- 判定：`allowed = (roots 为空 或 落在某个 root 之下) 且 不落在任何 deny 之下`。
  两侧一律先 `os.path.realpath()` 归一化再比较 —— 挡 `..` 和符号链接/junction 绕过。
  **判定只有一个所有者**（`files.path_ok(path, cfg)`），登记时与执行时**各判一次**
  （和 `send_pending` 的 `allowed_dirs` 二次校验同源：登记到确认之间配置可能变、文件可能被换成链接）。
- **边界放宽时启动打告警**，说明宽到哪（`agent.send_image_dirs` 那套规矩：
  边界可以宽，但**用户必须知道它宽在哪**）。

### 3.1 三处路径策略各管什么（不许含糊）

本项目会有三处「哪些路径可以」的判定。它们回答的是**三个不同的问题**，所以各有各的配置，
但每一处都必须在自己的文档/注释里写清管什么：

| 所有者 | 回答的问题 |
|---|---|
| `agent.send_image_dirs` + `image_cache` | 哪些**本地图片**可以**发出去**给别人 |
| `file_read` 的 `msg/file/` 边界 | 哪些**收到的**文件可以被读（微信落盘目录，按文件名匹配） |
| **`files.roots` / `files.deny`（新）** | 哪些路径可以在**盘上**被读写 |

## 四、触发者（谁能用）

- `files.who: []` —— 空 = **只认控制会话里、我自己发出去的那条消息**（你的口径「我的对话」）。
- 名单里可以加会话（你的口径「加指定对话」）。
- **闸门设在工具层**（`ToolBox` 构造时就知道自己在哪个会话），
  由 bot 主循环把「这条消息是不是我自己发的」这个**事实**传进来 ——
  判据留在**有事实的那条线程**上，而不是让工具层去猜。
- 不在名单里 = **如实拒绝并说清**（「这个会话不在 `files.who` 名单里」），
  **绝不静默降级**成「假装做了」或「假装没这个功能」。

> ⚠️ **必须让用户看见的风险**：指定对话里的对方发来的消息是**不可信的输入**
> （同 `web_read` 把搜索结果标成「不可信」那个理由）。如果名单里放了**别人**，
> 而写操作又是免确认的，那么**对方发一句话就能改你电脑上的文件**。
> 这不是 bug，是配置的后果 —— 所以：① 启动时把 `files.who` 的实际内容打出来；
> ② 文档里直说这条；③ `config.example.yaml`（发给别人的那份）默认**只控制会话**。

## 五、确认模型

- **整块开关 `files.enabled`（默认 `true`）**。关掉时**工具仍在 `TOOLS` 里、
  调用时如实拒绝**并说清「文件能力已关闭、在哪打开」——
  和 `shell.enabled` / `search.enabled` 同一条姿势（**不从 TOOLS 里摘掉**：
  摘掉的话 system_prompt 还教着一个不存在的工具，模型会反复试）。
- `files.confirm: [delete]`（默认）—— **要确认的 action 列表**。
  免确认的 action 直接执行；要确认的走 `set_pending(kind="fileop")`。
- ⚠️ **`delete` 永远强制确认**：即使有人把它从 `files.confirm` 里删掉，
  代码也要拦住并告警。**不可逆的那一步不给配置留后门。**
- 确认菜单里显示的是 **action + 原样路径**（同 `shell` 必须显示命令原文那条规矩）：
  中间任何转述/缩写/改写都等于把确认闸做废。路径长就截断，但**必须标注截断**。
- **删除实现：`ctypes` + `SHFileOperationW`**（已验证可用）：
  `FO_DELETE | FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_SILENT`
  - **零依赖、不起子进程**。已实测：`ctypes.windll.shell32` 可加载、`SHFileOperationW` 存在、
    结构体 56 字节（Python 3.11.9）。
  - 为什么不用 `send2trash` / `winshell`：**没装**，而且新增依赖会撞
    `envsetup.requirements_specs()` 那个坑（写成正式行 → 没装的人「装完还是起不来」死循环）。
  - 为什么不用 PowerShell：多一个进程；`health.py` 那条 PowerShell 路子是给**本地通知**用的，
    不是给文件操作用的。
  - `FOF_ALLOWUNDO` 是**唯一**让删除可恢复的旗标，**不许删**；`FOF_NOCONFIRMATION` 关掉
    系统弹窗（我们自己的确认闸在前面，不要再弹一个挡住轮询线程的对话框）。

## 六、配置：两份 config 用**不同默认值**

| 项 | 本机 `config.yaml` | 发出去的 `config.example.yaml` |
|---|---|---|
| `files.enabled` | `true` | `true` |
| `files.roots` | `[]`（全盘） | 桌面 / 文档 / 下载 |
| `files.deny` | 系统四目录 | 同左 |
| `files.who` | 控制会话 + 你指定的 | 只控制会话 |
| `files.confirm` | `[delete, overwrite]` | `[write, append, mkdir, copy, move, rename, delete, overwrite]` |

理由：本机按你的口径；但**发给朋友的包不该默认给「全盘 + 免确认写」**。

✅ 合规性已核实：`selftest_tool_registry.py` 第 4 项检查的是两份 config 的**段**是否对齐
（`set(config.yaml) - set(config.example.yaml)`），**不是值相等**。
所以两份用不同默认值是合规的，不会被那份自测判失败。

## 七、硬约束（都是不可谈的）

1. **跑在收消息那条线程上** → 单次操作必须有上限。大目录列举限量并**明说截断**；
   读大文件走 `file.max_chars` 分页（`cursor`），**绝不许把节选说成「全读完了」**。
2. **不许开线程**（hook 不支持并发）。耗时操作如实拒绝，不要偷偷后台跑。
3. **删除不可逆** → 每次单独确认，菜单显示原样路径。
4. **失败如实说**，绝不静默降级、绝不假装成功。
5. **系统目录默认挡住**，且 `deny` 只能由用户改，代码不许自己放宽。
6. **不执行程序**（这条是本工具与 `run_command` 的分界，不许模糊）。
7. **`read` 对目录要如实拒绝并指路**（「这是个目录，列目录请用 `list`」），
   不许抛一个原始异常上去，也不许把目录当文件读出一堆乱码。
8. **任意磁盘路径来源的文件，绝不许走「名单内直发」**（见 2.1）：
   一律进确认队列，且确认菜单显示**原样路径**。这条不给配置留后门。

## 八、接线点与已知的坑

| 位置 | 改动 |
|---|---|
| `agent_tools.TOOLS` | 新增 `computer_files` 一条（built-in，走适配层进注册表） |
| `agent_tools.set_pending` | 新增 `extra=None`（dict），整包存 |
| `agent_tools._action_key` | ⚠️ **必须把 `extra` 算进判重键**（见下） |
| `bot.restore_pending` | 透传 `extra`（⚠️ 见插件规格 4.1：不改这里，重启后那条待确认项会**静默退化**） |
| `agent_tools.describe_pending` | 新增 `fileop` 分支 → action + 原样路径；`kind=="file"` 分支**按 `extra` 的来源标记分级显示**（2.1） |
| `agent_tools.send_pending` | 新增 `fileop` 分支 → `files.apply(item, cfg)`；`kind=="file"` 分支的 `allowed_dirs` 二次校验要**同时认 `files.path_ok`**（登记到确认之间配置可能变） |
| `agent_tools.t_send_file` | 定位口径放宽为 `msg/file/` ∪ `files.path_ok`；**磁盘来源一律进确认队列、跳过名单直发那条分支**（2.1） |
| `bot.py` 主循环 | 把「这条消息是否 `from_self`」与 `files.who` 判定结果传进 `run_agent`/`ToolBox` |
| `config.yaml` + `config.example.yaml` | 两份都要加 `files:` 段**和**教 `computer_files` 的 system_prompt 指导 |
| `CLAUDE.md` | ⚠️ **先腾空间**（现 65156/65536 字节，只剩 380）—— 见插件规格第八节 |

> ⚠️ **`restore_pending` 的坑再强调一次**：它是**逐字段白名单**传参的
> （`bot.py:1179-1191`）。历史上 `label` / `items` / `spec` / `file` 都因为漏了一处而
> **静默退化**成别的操作（群发批次退化成「往空 wxid 发预览文字」= 真机上「发出去了但没人收到」
> 这种最难查的错）。新 kind 的字段**一律走 `extra`**，`restore_pending` 整包透传。

> ⚠️ **判重键的坑（会删错文件，比上面那个更危险）**：`agent_tools._action_key`
> （`agent_tools.py:1609`）是一个**写死的字段元组**，不含 `extra`。
> 「删掉 A」和「删掉 B」两条 `fileop` 的 `kind` 相同、`to_wxid`/`text` 全空
> → **判重键一模一样** → 第二条**不登记**，用户看到「已经有一条相同的了」，
> 照菜单回「确认」**删掉的是 A**。所以本能力落地时
> **`_action_key` 必须把 `extra` 算进去**，并给一条回归用例直证两条不同的 fileop
> **不会被判成同一条**。

## 九、回归用例（`selftest_files.py`）

| 分组 | 用例 |
|---|---|
| 路径 | `roots` 空 = 全盘放行 / 落在 `deny` 下被拒 / `..` 绕过被拒 / 符号链接绕过被拒 / `roots` 非空时根外被拒 |
| 闸门 | `delete` **强制**确认（配置里删掉也拦，且告警）/ 免确认 action 直接执行 / 非 `files.who` 会话被拒且**说清原因** |
| 回收站 | 自建临时目录里删一个临时文件 → `SHFileOperationW` 返回 0、**含 `FOF_ALLOWUNDO` 旗标**、原路径已消失。**只碰自建的临时目录，绝不碰真实用户文件**。⚠️ 「真的进了回收站」这一条**自测证不了**（要枚举回收站得走 Shell COM，代价过大）→ 归到 `verify_real.py` 的**真机人工确认**项：删一个测试文件，人去回收站看一眼它在不在。**不要把没验证的说成验证过了。** |
| 复用 | `read` 走的是 `file_read.extract()`（用桩证明**同一条内核**，不是另写一份） |
| 确认队列 | `fileop` 待确认项经 `set_pending` → `restore_pending` 之后**字段一个不少**（防静默退化） |
| 判重键 | 两条**不同**的 `fileop`（如删 A / 删 B）**不得**被判成同一条；两条**逐字相同**的仍应判重 |
| 发盘上文件 | 磁盘路径来源的文件：**即使收件人在 `auto_send_whitelist` 里也进确认队列**（反向证明直发那条分支没被放宽）；`msg/file/` 来源的老行为**逐字不变** |
| 菜单分级 | `msg/file` 来源 → 菜单只显示文件名；磁盘来源 → 显示原样路径，且长路径截断**必须标注** |
| 覆盖闸 | `write` 命中已存在文件且没有 `overwrite=true` → 如实拒绝；给了 `overwrite=true` → 进确认队列（不直接写） |
| 截断 | 大目录 `list` 明说「还有多少没列」；大文件 `read` 给 `cursor` 且**不说「读完了」** |
| 边界不重叠 | `computer_files` 不能执行程序（拿 `run_command` 的用例反向证明本工具没有 exec 参数） |

## 十、ADR 信号

- **新增 owner**：`files.py`、`docs/computer-files-spec.md`
- **安全边界变更（ADR 级，要单独落档）**：
  这是本项目**第一次让模型获得免确认的写盘能力**。此前的不可逆动作（发消息、跑命令）
  一律走确认闸；`web_read` 把外部内容标成「不可信」的理由原文就是「模型手里有
  send_text / run_command」。现在加上免确认的写/移动/重命名，**赌注变大**，
  必须作为一条 ADR 记下来：默认值是什么、谁批的、怎么收紧、怎么发现被滥用。
- **另两条同为 ADR 级**（都要写进同一条 ADR）：
  ① `send_file` 的可达文件集从「微信里收发过的」放宽到**盘上任意白名单路径**
  —— 明确的结论是**这条放宽不连带放宽「名单内直发」**（2.1），否则就是一条
  「把盘上任意文件免确认外发」的通道；
  ② `_action_key` / `restore_pending` 从「人手维护的字段列表」改成
  **`extra` 整包 + 注册表声明的 `key_fields`**（插件规格 4.1 / 4.2），
  这是把两类静默失效**结构性**消掉的改动。
- **依赖方向**：`files` → `plugins`（注册进契约）、`files` → `file_read`（复用抽取内核）；
  `file_read` **不反向依赖** `files`。
- **回收站实现选择**：`ctypes` + `SHFileOperationW`（零依赖、不起子进程），
  否掉了 `send2trash` / `winshell`（新依赖）与 PowerShell（多进程）。
  这条要写进 ADR 的理由栏，否则以后有人会「顺手」换成 `send2trash`。
