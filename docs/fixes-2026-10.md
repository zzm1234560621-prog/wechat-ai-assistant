## 五、已知遗留/未做（如实记录）

1. **`usage` 已接线（本轮补上）**：`llm.py` 的四个返回点各调一次
   `_rec_openai` / `_rec_anthropic`（anthropic 与 openai 两协议 × `chat` / `chat_with_tools`），
   只记 `ts/provider/model/prompt_tokens/completion_tokens/kind`，不记请求内容与密钥。
   - 已实测：喂假响应 → `data/usage.jsonl` 落 3 行、`usage.summary()` 汇总正确、
     键集合恰好 6 个（无 `api_key`/`content`）。
   - 只记**成功拿到 usage** 的调用 ⇒ 是本地估算、不是账单；价目表只有
     `deepseek-chat` / `deepseek-reasoner`，其余模型只报 token 不算钱。
2. **`action: call`（定时打电话）仍未打通。** hook 没有任何通话接口，`run_due` 到点只会**如实报错并通知用户**，不会偷偷改成发文本。
3. **`health.notify` 的桌面气泡通知未经真机确认。** 实现是 best-effort 的 PowerShell + `NotifyIcon`（10 秒超时、失败只告警），自测里**故意把通知函数换成假的**，所以「气泡到底弹不弹得出来」没有证据。
4. **`status_page` 的「绝不查库」只保证不主动查。** 它作为 HTTP 服务会起一个 daemon 渲染线程；该线程只调用调用方传进来的 `snapshot_fn`（即 `Health.snapshot()`）。**只要传入的 `snapshot_fn` 不去查库，它就不查库**——这条约束靠接线纪律，不靠代码强制。
5. ~~`console.py` 的「一键自动」仍是旧逻辑~~ **已在复核后修掉**：`console.auto()` 现在对 4.x 会直接说明「走 aixed hook 主线、不需要 wcferry、也不要降级」并退出（不再弹降级确认）；`wechat_version.match_wcferry()` 对 4.x 的文案也改成指路而不是劝降级。`降级.bat` / `助手.bat [1]` 仍在（那是 wcferry 后端的正当工具），README 已标注「4.x 主线别走」。
6. **`wechat_version.WX_TO_WCFER` 里只有一条版本号是核实过的。** 表里原本是三位短号（`39.5.2` / `39.4.4` …），而 PyPI 上 wcferry 的版本是**四段**（实测 `39.5.2.0` 有、`39.5.2` 没有）→ `pip install wcferry==39.4.4` 会直接 No matching distribution。已把**有旁证可核实的** `3.9.12.51 → 39.5.2.0` 改对（GitHub issue 上的配对 + PyPI 存在性），**其余几条仍标着「⚠️ 未核实」**并写明「别凭猜补 `.0`」。`downgrade.py` 里手抄的第二份表已删掉，改成从 `WX_TO_WCFER` 派生（单一真源）。要修剩下的，得先去 PyPI 的版本历史对出四段号。
7. **`health.notify` / `status_page` 的参数没有真机跑过完整一天**（`alert_cooldown` 的 1 小时是否合适未验证）。
8. **hook 安装脚本里写死了本机路径**（`do_hook_install.ps1` 的 `$WX` / `$UPD` / `$USER`）。换机器必须先改脚本开头三行——README 已提示，但脚本本身仍是「本机自用」形态，没做成参数化。
9. **改完配置后没有真机跑过一遍 bot**（按任务约束：不启动 `bot.py`、不碰 127.0.0.1:30001）。所以本轮的一切结论都来自**代码阅读 + 自测**，不含端到端真机验证。
10. ~~「补齐期」异常丢消息（复核者报的理论问题）~~ **已实测，不成立**。
    - 复核者的机制是：「消费者处理第 k 条时抛异常 → 异常在 yield 点倒灌回生成器、把它终止 → 本批第 k+1..n 条再也不会 yield → 永久静默丢」。
    - **实测结论：不会。** 消费者侧抛出的异常**不会**终止那个挂起的生成器——只要它还被引用着（`main()` 的局部 `source` 一直持有），下一次 `next(source)` 会从 `yield` 之后**继续把本批剩下的消息发完**。
      - 实验（纯语义）：3 元素生成器，取 2 个后抛异常，再取 → 拿到第 3 个（`[1, 3]`）。
      - 实验（真身 `iter_aixed_messages` + 假 client，一批 3 条）：`[1, 2, 3]` —— 一条没丢。
      - 回归用例钉在 `selftest_bot_loop.py` 的 `t_batch_survives_consumer_error`。
    - 所以**不需要**把「按批取」改成「按条取」，主循环结构保持不动。
11. **轮询持续失败会刷屏（已修）**：`iter_aixed_messages` 里 `poll_messages` 抛异常原本每次都会打（`AixedError` 打一行，其它异常打**完整 traceback**）。实测 `poll_interval=0.01` 时 **2 分钟刷出 5.4MB**；生产值 5 秒也等于「每 5 秒一条 traceback、永不停」，会把 5MB 的日志轮转刷穿、把真正的线索淹掉。已改成按 **1/10/50 次**打印、之后每 50 次提醒一次（和 `live_history._note_poll_error` 同一路子），成功一次即清零。
12. **`config.yaml` 里 `agent.send_image_dirs` 被用户设成了 `test_images`**，这会**覆盖**默认的「微信图片缓存根」白名单。所以「聊天里的图还发不发得出去」这条**必须真机验**：先把该键清空回到默认，再用真 hook 发一张缓存缩略图。13. **`usage.jsonl` 里现存的 token 全是 0**：那几行是**自测造假响应**写进去的，说明不了真实调用。真实调用下的 `extract_openai_usage` / `extract_anthropic_usage`（尤其 anthropic SDK 对象形状）**还没被真实验证过**。
14. **`status.enabled` 默认关**，`status_page` 从没真跑过完整一天；端口冲突、真实 `Health.snapshot()` 的渲染（含 `poll_errors` 的 tuple→list）都只在自测里覆盖过。
15. **`health.notify` 的气泡**是否真弹、两个位置参数顺序对不对，只能真机看（自测里 `notify_fn` 被换成假的）。

## 六、真机联调发现并修掉的收图缺陷（用户报「发图不动」）

**症状**：用户在文件传输助手里发了一张图，bot **一点反应都没有**（不是「回了但答错」，是根本没进处理）。

**定位过程（先证伪再证真，两条假设都被推翻了）**：
1. 先怀疑「中文文件名发不出去」——**证伪**。做对照实验：同一张图分别用中文名和 ASCII 名发给
   文件传输助手，两种都返回 `{"ret":0,"retmsg":"success"}`，而且**都真的落库了**
   （`Msg_9e20f478…` 里 `local_id=455/456`、`local_type=3`）。用户也确认看到了图。
2. 再怀疑「图片不在 fts 里」——**证实**。四个 fts 分片
   `SELECT COUNT(*) … WHERE local_type = 3` **全是 0**；而同一时刻 filehelper 的 `Msg_` 表里
   图片一行不缺（`local_id 454/455/456`，`local_type=3`）。也就是说
   **微信的 fts 只索引有文本内容的行，图片一条都不进**。

**根因（L5：跨系统契约 —— 两条收消息通路各漏一半）**：
* 主路 `_v4_new_messages` 用 **fts rowid 游标** → 图片压根不在 fts 里，永远扫不到；
* 兜底路 `_v4_new_messages_session` 用 `SessionTable.summary` → 图片的 summary 是**空串**，
  被 `if not content: continue` 跳过。
→ **任何会话里别人发来的图片，两条路都看不见**。这不是「渲染问题」，是**根本没收到**。

**修复**（`live_history._v4_pickup_nontext`，接在 fts 轮询之后）：
用 `SessionTable` 当「有新动静」的信号，条件收紧到 **`last_timestamp >= 游标 AND summary` 为空**
（= 最后一条不是文本）才回查那个会话的消息表；每个会话一个水位线
`cursors["__nonttext__"][talker]` 防重复。**稳态下那个 session 查询返回 0 行 → 零额外查询**。

> ⚠️ **踩过一次的坑（写完第一版才在真机上发现）**：第一版加了「第一次见到某会话只记水位线、
> 不报」的 seed，想借此避免重启时回放历史图片。结果它把**「你在某个会话里发的第一张图」
> 也 seed 掉了**——那个会话还没进水位线，图就永远报不上来。
> 启动边界其实已经有三道现成机制挡着，不需要再挡一次：`last_timestamp >= since`
> （since 是 fts 游标，启动时即最新）、`prime()` 把边界消息塞进 `seen` 去重、
> 以及 bot 主循环的 catchup 判定（停机期旧消息只通知不自动回复）。**seed 已删除。**

**连带处理**：
* `aixed_api.Msg` 带上 `local_type`（上层要能区分文本/图片）；
* 补捞之后**我们自己发出去的图也会回显**成一条新消息（文本有 `remember_sent`/`is_own_reply`，
  图片没有）→ 新增 `agent_tools.remember_sent_image()`（三处发图路径都调）+
  `is_own_image()`（30 秒时间窗），主循环据此跳过自己的回显；
* 顺带修 `aixed_api._check`：**只认 `status`、不认 hook 实际用的 `ret`**，
  于是 `{"ret":-1,"msg":"invalid json"}` 被当成功吞掉 —— 现在两种都认（含 `"-1"` 字符串形式）。
  但**限度要写清楚**：`/SendImgMsg` 成功也是无条件 `{"ret":0}`（hook 侧 `SendImage` 是 void、
  连 `HeapAlloc` 失败都只是 `return`），所以「没报错」**不等于真发出去了**。

**这一条修不了、只能如实说的**：v3（wcferry 3.9.x）那条 `_v3_new_messages` 用的是
`WHERE Type = 1`，**同样看不见图片**。v3 是保留后端、本机无法验证，本轮未动，记在这里。

### ① `file.max_bytes: 0` 把**整条音频路**打死了（真 bug，已修 + 已上回归）

现场：`file.max_bytes: 0`（=不限，2026-10-02 起的新默认）时，**任何非空音频都被拒**：
「这个音频 0.1MB，超过上限 **0.0MB**」。根因在 `audio_read._precheck`：

```python
cap = int(max_bytes or _max_bytes(cfg))     # ← _max_bytes 把 0 当"没配"，算出上限是 0 字节
```

`file_read._opt_int` 那个「0 和没配必须分开」的坑，**音频这一支漏了**。
`file_read` 那边修过、音频这边没有，所以文件能读、音频全废 —— 而且**测试没覆盖 0 这个默认值**，
只有 `max_bytes: 8` 那种用例，于是全绿。

修：`_max_bytes` 只判「键在不在」（不在才退回 30MB，在就原样用，哪怕 0）；
`_precheck` 里 `if cap and size > cap`（0 = 不限，跳过）。回归：
`selftest_audio.t8_max_bytes_zero`（含端到端：0 时真能读到文字）。

### ⑤ 怎么判断「运行中的 bot 到底装的是哪份代码」

Python **只在启动时**读一次模块和 `config.yaml`。所以**改完代码不重启，改动不生效**，
而且表面上完全看不出来（日志照常、功能照旧）。两个反例都真实发生过（2026-10-03）：

* 改完 `voice_mem.py` 以为已经在跑，其实那次进程加载的是改动前那一份；
* 同一批改动分几次落盘（22:44 / 22:57 / 22:58），于是**同一个 bot 是"混合版本"**：
  有 22:33 的语音定位修复，却没有 22:44 的兜底路修复、也没有 22:57 的扫描预算。

**判据（一行就够）**：拿 `data/status.json` 的 `started_at` 去比文件的 mtime：

```powershell
(Get-Content data\status.json -Raw | ConvertFrom-Json).started_at
Get-ChildItem bot.py,voice_mem.py,live_history.py,config.yaml | Select Name,LastWriteTime
```

**mtime 早于 `started_at` ⇒ 这个进程加载了它；晚于 ⇒ 没加载。**
（`started_at` 是 `health.Health` 自己落的运行快照，比推算心跳可靠。）

⚠️ **但 `status.json` 只在心跳时写 —— 也就是最多滞后约 150 秒**（见第 ④ 节的实测）。
刚重启完那一两分钟里，它里面还是**上一个进程**的 `started_at`，照它比会得出
"没加载新代码"的**错误结论**（2026-10-03 当晚就这么误报了一次）。

⇒ **刚重启后要立刻判断"到底起没起、装的是哪份代码"，先看 `bot.log` 的启动块**
（`[bot] 正在连接 aixed HTTP 服务 …` + `[bot] 轮询模式：游标 = …`，
这两行是**启动当刻**写的，不等心跳）；等过了第一个心跳再拿 `started_at` 复核。

`config.yaml` 同理——它也是**启动时**读一次，改完不重启不生效。

### ⑥ 「这条语音到底多长」可以不查库就问出来

`voice_mem.read()` 会把每条真的送去转写的候选落成一个 WAV，文件名就是
`<内容摘要>_<目标毫秒>.wav`（写盘目录 `data/voice_mem/`）。所以：

```powershell
Get-ChildItem data\voice_mem\*.wav | Sort LastWriteTime -Desc | Select -First 3 Name,LastWriteTime
```

看**文件名里的毫秒**（= 消息 XML 的 `voicelength` 那一路的目标时长）和 mtime，
就能在**不查库、不停 bot** 的情况下知道"刚才读的是多长的一条、什么时候读的"
（2026-10-03 就是这么确认"一条 **7.74 秒**的新鲜语音读出来了"的）。

## 2026-10-04 · 待确认队列出现两条**一模一样**的动作（真机）——判重放在**入队**那一头

### 现场

用户在控制会话里连着三遍要同一份文件（「最新的发给我吧」→「吧文件发给我」→「发给我吧」），
助手每一遍都照做、各登记一次待确认。于是菜单里出现：

```
1) 把文件「2026-2027 BNIS …课表.xlsx」发给 Nova Academy Campus 2026-2027
2) 把文件「2026-2027 BNIS …课表.xlsx」发给 文件传输助手
3) 把文件「2026-2027 BNIS …课表.xlsx」发给 文件传输助手
```

第 2、3 条**逐字相同**。用户回「确认 2」发了一份，再回「确认 3」**又发一份**——
他当场问「这个确认2和确认3有什么区别啊」（`bot.log:3855/3861` 两次登记，
`bot.log:3888-3893` 菜单，`bot.log:3905` 确认 2 真的发出去了）。

### 根因

`agent_tools.set_pending()` 无条件 `append`。系统里**没有任何地方认得**「这同一条动作
已经在队列里了」：用户每说一遍、模型就登记一遍，队列就长一条。这是**队列自己的**缺，
不是模型的错（模型每次做的都正是它该做的事）。

⚠️ 和 2026-10-03 那个「重复发」**不是同一个根因**，别搞混：那一次是**发出去的文件回显**
成新消息、又被当成新请求（已由 `remember_sent_file` / `is_own_file` 认掉）。
这一次文件**一个字都还没发**（两条都还在待确认），是纯重复入队。

### 修法（判重在唯一写队列的地方）

* `set_pending()` 先给新条目算一份「动作身份」（`_action_key`：`kind` + 收件人 + `count`
  + 真正要发的那份东西 —— 文件路径（realpath）/ 图片列表（保序）/ XML / 命令原文 / 正文 /
  群发 `items`+`spec`），再拿它去比**这个会话里还没过期**的条目（`_dupe_index`）：
  命中就**不 append**，返回那一条的**菜单编号**。
* 工具侧 9 个登记点统一走 `ToolBox._queue_send()`（判重 ttl 只在这一个口子拼），并把
  `dupe_note(编号)` 接在返回文本后面 —— 模型因此知道「这次没有再排一条」，不会对用户
  说成「我又给你排了一条」（菜单里只有一条，说了就对不上）。
* 群发 `prepare_broadcast()` 同样判重，并**写进那段原样直发给用户的报告**里。
* `restore_pending()` 把 ttl 传进去，所以**旧版本留在盘上的重复条目只会恢复一条**
  （自愈），恢复条数只算真的恢复了的那些。

### 四条边界（别改回去）

1. **`kind="auto"`（自动回复草稿）完全不判重。** 它不是「用户要求的一个动作」，而是
   「响应某一条消息生成的回复」——两条一样的草稿对应**两条不同的消息**，合并掉就是
   **第二条消息没人回**（静默少发比重复更坏）。防刷屏靠 auto_reply 自己的冷却。
2. **`count` 算进身份**：`count=2` 和 `count=1` 不是同一件事，合并＝静默少发一条。
3. **只认还没过期的条目，而且过期项只跳过、不删。** 拿一条早就过期的旧条目去拦新请求，
   等于把用户的新请求吞掉（工具回「请回确认」、用户回确认时队列却是空的）；顺手删队列项
   是读侧（`_alive`）的事，入队这边不动它。
4. **判重命中会把那条的 `ts` 刷新成现在。** 用户刚又说了一遍同一件事，确认窗口就该按
   最后一次请求重新起算；不刷新的话，一条还剩 3 秒过期的相同条目会把这次请求「吃掉」。

### 「确认」有效期只有一个解析

`agent_tools.confirm_ttl_of(cfg)`：判重窗口、bot 的确认分支、`save_pending` /
`restore_pending` 全走它。以前是四处各自 `int((cfg.get("agent") or {}).get("confirm_ttl", 300))`
—— 判重窗口一旦和读侧不一致，两头都错：比读侧大＝吞掉用户的新请求，比读侧小＝同一条
又能重复入队（这个 bug 换个窗口就复发）。

### 回归

* `selftest_policy.test_pending_dedupe`：① 判重；② 不许误并的五种差异（正文/收件人/kind/
  count/图片顺序）+ `auto` 例外；③ 过期不拦也不删；④ 刷新时效；⑤ `dupe_note` 不泄 wxid；
  ⑥ `confirm_ttl_of`；⑦ 工具级「同一份文件同一人发两遍」。
* `selftest_bot_loop.t_pending_persist` 里那条「盘上两条一模一样的 → 只恢复一条」。
