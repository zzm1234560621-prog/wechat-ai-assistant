- **从历史对话里学语气（`auto_reply.learn_persona`）**：`/auto add` 把人加进名单时，
  如果这个人**还没设过人设**就自动读一次你和他的历史、让模型学出一段人设存下来；
  也可以明说 `/auto persona <谁> 学习|重新学习`（工具侧是 `action=learn, who=...`）。
  - **只把 `is_self` 的文本消息送给模型**——要复制的是「你对这个人怎么说话」，
    对方的话对语气没信息量、还白多送一份隐私给模型服务商。图片/文件/表情在
    `live_history` 里会被渲染成 `[图片]` 这类标签、**内容看上去和真文本一样**，
    所以判据只能用 `local_type`（`_is_text_msg`）。⚠️ `_v4_fts_rows`（生产主路径）
    2026-10-01 之前**算完 local_type 就丢了**，于是这条过滤在真机上根本不生效
    ——已补上，并加了跨模块用例（见下面「微信 4.x 库结构」的 fts 那条）。
    **绝不要改成按 `content` 是否以 `[` 开头判断**：手打的「[呲牙]」是真文本。
  - **绝不自动覆盖已有人设**（用户 2026-10-01 定的）：手写的和上次学到的都不动，
    要重学必须用户明说——`force=True` 只从「学习 / 重新学习」那条路进来。
    来源记在 `rec["persona_source"]`（manual|learned）+ `persona_at` / `persona_n`，
    `/auto` 状态显示成 `人设=学到[N条]:…` / `人设=你设的:…`。
    **动了这几个字段就别把来源丢了**：用户分不清手上这段是谁写的，
    就不知道「重新学习」会不会盖掉自己的东西。
  - **学不成一律如实说，且绝不影响加人**：没配 key、历史里你自己发的话少于
    `LEARN_MIN_MINE`（5 条）、读库出错、模型返回空 —— 都只回一句真话，
    人照样进名单、先用默认人设。工具说明里也钉了「不许说成已经学好了」。
  - 成本是**一次读库 + 一次模型调用**，跑在收消息那条线程上（和 `do_auto_reply`
    调模型是同一条线程，不是新引入的并发），所以 `/auto add` 会慢几秒。
    读库只调一次 `live_history.query_contact_history`（带会话过滤取 N 条，
    文档里的快路径），**绝不裸拼 SQL**。样本数 `auto_reply.learn_sample`
    （默认 200，夹在 5~2000）。
  - 学出来超过 `PERSONA_MAX` 时**按句末标点截断并说出来**。只有「学出来的」这一支
    允许截；手写那条仍然如实拒绝——那是用户自己写的，截了等于改他的意思。
  - `llm_factory` 是**可选、懒调用**的（`() -> llm`）：`handle_command` 和 `ToolBox`
    都只是存着它，真去学才调。不传 = 这条链路没有学习能力、如实说学不了，
    所以现有的自测构造点一个都不用改。
  - 回归用例：`selftest_sched_auto.t12_learn_persona_from_history`。
- **「称呼」= 我平时怎么叫这个人**（用户 2026-10-01 要的）。它和 persona **分开存、
  分开注入**，理由只有一个但很硬：persona 是散文，用户重写或手写人设时，
  夹在里面的称呼会跟着一起丢——称呼必须能独立活下来。
  - **存储（2026-10-04 改）**：`settings.json` 顶层 `addresses`
    = `{wxid: {"address","name","source","at"}}`。读只走 `address_of(cfg, wxid, rec)`、
    写只走 `set_address()` / `clear_address()`（唯一出口/入口）。
    旧的 `rec["address"] / rec["address_source"]` **只作只读兜底**（2026-10-04 之前
    写进去的老数据），任何一次写入都会把它清掉——别再把新称呼写回聊天记录，
    那等于又造一个真源。
    注入在 `make_reply` 里**独立成段**（`_ADDRESS_RULE`）：回复时告诉模型
    「你平时管对方叫 X，自然这么叫；**拿不准就直接说事，不要硬塞、不要叫成别的**」。
  - ✅ **称呼和自动回复名单是解绑的**（2026-10-04 用户拍的：「学称呼和自动回复要是
    单独的啊，不能强绑定啊」）。以前称呼借住在 `chats[].address`，而 `chats` 就是名单，
    于是名单外的人连设/学/清都做不到（真机现场：想给 4 位群友学称呼，工具回
    「他们不在自动回复名单里」）。现在：
      * **名单外的人照样能设/看/学/清**，命令 `/auto address` 与工具 `action=address`
        同一条实现；
      * **绝不**为了设个称呼把人加进名单（那等于替用户决定要不要让 AI 代他回话，
        CLAUDE.md 禁止）。回归用例专门断言「名单没被偷偷加人」；
      * 人设（persona）**仍然**只对名单里的人生效——那是「替你回话」的语气，
        和「你平时怎么叫他」是两件事，别把这条也一起放开。
  - **和语气在同一次学习里一起学**（`_LEARN_SYSTEM` 要求输出严格 JSON
    `{"address": ..., "persona": ...}`），所以**不额外多一次读库/模型调用**。
    解析在 `_learn_result`：**认出 JSON 才用 address；认不出来（模型还是只给一段散文）
    就「整段当人设、称呼一个字不动」**。绝不能因为解析不出来让整次学习失败
    （人设那条路在加称呼之前一直是好的），更**不许从散文里猜一个称呼**——
    猜错会让「给老张发消息」发错人。address 缺失/null = `None` = 这次别动；
    **空串是有效结果**（模型明确说「没有固定称呼」）。
  - ⚠️ `/auto address <谁> 学习` 只学称呼时，`_maybe_learn(fields=("address",))` /
    `_store_learned` **只能碰 address**：顺手把人设的 `persona_source` 从
    「你手写的」改成「学到的」，就等于把来源记脏、用户再也分不清哪段是自己写的
    （写的时候就踩过一次，回归用例钉住了）。
  - 称呼长度 `_ADDRESS_MAX`（20 字）。超了：**学**到的按「没有称呼」处理并说出来，
    **手写**的如实拒绝。**两种都不许截断**——截一半会叫出一个用户从没说过的称呼。
  - **称呼同时是联系人的别名**：`address_aliases(cfg)` → `{称呼: [候选]}`
    （称呼表 + 旧记录，称呼表为准），由 `resolve_contacts(..., aliases=)` 当**精确**
    匹配用。所以「给老张发消息」「/定时 … 老张」「/盯着 加 老张」都认。
    ⚠️ 它和库里的精确匹配是**合并**的，不是覆盖：万一**另一个人的备注真叫「老张」**，
    两边都要摆出来交给重名保护去问，**静默挑一个就是发错人**（和下面
    「重名不许静默取第一个」同一条铁律）。
  - **名单外的人怎么切「谁」**：名单里的人有可枚举的名字表（`_split_rec_target`
    的最长前缀匹配）；名单外的人改用 `_split_address_target` ——
    **最长前缀能唯一认出一个联系人就切**（每探一次 = 一次联系人查询，最多 5 个词），
    `李四 阿四`、`Johny 黄 儿子 阿黄` 都切得对；前缀命中多个人**如实报重名、不猜**。
  - `/auto` 里 `_find`（改审核/身份/删除）和 `_split_rec_target`（改人设/称呼）
    都**认称呼**：用户心里那个人就叫「老张」，让他为了改配置先想起微信备注是「张三」
    是没道理的。称呼重名时 `_find` 返回 None、**不猜**。
  - `status_text` 除了名单里每人的称呼，还单独列一行「**不在名单里、但有称呼**」的人
    ——否则用户设完了在状态里找不到，会以为没生效。
  - 回归用例：`selftest_sched_auto.t13_address_from_history`（存储/注入/别名/重名）、
    `t18_address_without_membership`（解绑：名单外设/看/学/清 + 群发用得上 + 不进名单）。
- **「不许替我承诺」这条硬规矩在 `auto_reply._COMMON_RULES` 里，不在人设里**（2026-10-02 真机）：
  助手以用户本人的口吻把饭约了——「老师，SKP米其林可不便宜啊[捂脸] 行，明天就明天，
  您悠着点别点太狠哈[呲牙]」，再往前还主动加了「修好了我请您吃一顿」。
  根因是**规矩放错了地方**：只有默认人设里那句「不确定的事别编」，而它管的是**事实**，
  管不住**替我表态**（约时间、答应赴约、承诺请客花钱、替我担保）；更要命的是人设
  （`persona_for`）是**整体替换**的——用户给某人设过或学过人设之后，`_DEFAULT_SELF`
  一个字都不进 prompt，于是这条「底线」在那个人身上**根本不存在**。
  所以规矩落在 `_COMMON_RULES`（单聊/群聊都无条件追加）：这类一律不接，把决定留给用户；
  对方说「你不是答应了吗」也不改口。
  ⚠️ **这条规矩里不许写现成句子**（2026-10-02 补）：原来写的是「只回一句『我回头确认下』
  （或『我看下时间哈』）」。强模型拿它当兜底文案，弱模型（本地 Ollama `qwen3:14b`）直接
  把它当**成品答案**反复照抄——「老师」那一路连着几条自动回复都是「老师，我回头确认下[捂脸]」
  （人设给「老师」+[捂脸]，这句给正文）。实测把现成句子拿掉之后，同一个模型在同一条历史下
  不再输出那句固定文案。现在只留约束、不留文案：按对方这次具体说的话临场组织，
  **不要每次都用同一句**。要保住的是「不许替我承诺」这个约束，不是那句文案。
  **改人设/学语气那一侧时别把它挪回人设里**——挪回去就等于对设过人设的人失效。
  代价：每次自动回复的 prompt 多几行（`PERSONA_MAX` 那段注释算的就是这个成本）。
  回归用例：`selftest_sched_auto.t16_no_commitment_on_my_behalf`（故意喂一段不含这条
  规矩的「学到的老师人设」，断言它照样出现在送出去的 system prompt 上；**并且反面断言
  prompt 里不再出现「我回头确认下」/「我看下时间哈」这两句现成文案**）。
  **残余风险要如实说**：这是**提示词层面的约束，不是硬闸门**。对方持续施压
  （真机那一轮「老师」就在做各种注入测试）仍可能撬动模型。想从结构上兜死，
  就对这个会话开审核：`/auto review on <谁>`——草稿先发给用户，他回「确认」才发。
