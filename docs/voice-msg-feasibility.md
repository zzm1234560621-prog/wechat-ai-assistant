# 微信语音条 → 文字：可行性评估（只读结论，未实现）

> 2026-10-01 实探。**结论：当前不可行**，卡点不是「转文字」（STT），而是**拿不到音频字节**。
> 本文只评估，不含实现。真正要做时按下面「下一步」的顺序推进，每一步都有证伪点。

## 一、已证的事实（都是这台机器上实测的）

| # | 检查 | 结果 |
|---|---|---|
| 1 | hook 暴露的 HTTP 路由 | 只有 8 个：`/QueryDB/execute`、`/QueryDB/status`、`/QueryDB/GetAllDBName`、`/SendTextMsg`、`/SendImgMsg`、`/ForwardXMLMsg`、`/GetSelfProfile`、`/Decode_Pic`。**没有任何语音接口** |
| 2 | hook 源码里搜 `Voice/voice/Silk/silk/Amr/amr/语音` | **零命中** |
| 3 | 82 个 `msg\attach\<md5>\<月>\Rec\`（语音条该在这） | **全是空的，0 个文件** |
| 4 | 全账号目录搜 `.silk/.amr/.aud/.mp3/.wav/.ogg/.m4a/.aac/.speex` | 只有 **15 个 `.m4a`**，全在 `msg\file\<月>\`，即**当文件发来的音频**（明文，已被 `audio_read` 覆盖）；**没有任何语音条文件** |
| 5 | 有没有「解码后的语音」缓存（类比图片的 `cache\...\Thumb\*.jpg` 明文缓存） | **没有** |
| 6 | `message_0.db` 的表（290 张） | 全是 `Msg_*` + 基础设施表；**没有 audio/voice/trans 相关表** |
| 7 | `Msg_*` 的列 | `local_id, server_id, local_type, sort_seq, real_sender_id, create_time, status, upload_status, download_status, server_seq, origin_source, source, message_content, compress_content, packed_info_data, WCDB_CT_*`。**没有语音文本列**（只有 `source` 可疑，见路线 1） |
| 8 | 各 fts 分片最近 4000 行（≈1.6 万条）里 `local_type = 34`（语音） | **命中 0 条** —— 这台机器近期**没有语音条样本** |
| 9 | 落盘媒体的加密 | 见 `docs/wechat4-dat-image-notes.md`：`.dat` 格式已确定、**XOR 段密钥 `0x6C` 已破解**，但**AES 段的固定密钥没拿到** |

**为什么第 3 条是致命的**：3.9.x 时代微信把收到的语音明文写成 `Rec\*.amr`，直接读就行；
4.x 这条目录**根本不落东西**。所以「读语音」缺的不是解码器，是**字节本身**。

## 二、三条候选路线（按性价比排序）

### 路线 1：微信自带的「转文字」会不会落库（唯一可能零逆向的捷径）★先做这个

微信长按语音条有「转文字」。如果结果被写进 DB（`source` 列或别的字段），那我们**只要读它**，
不需要任何逆向——代价是用户得先长按转一次（体验差，但能立刻验证「到底有没有这条路」）。

- **验法**（需要用户配合，见第四节）：找一条语音条，**转文字前后**各查一次那一行，
  对比 `source` / `compress_content` / `packed_info_data` / `SessionTable.summary`。
- 证伪点：如果前后**一个字节都没变**，说明转文字只在内存里、不落库 → 这条路断，转路线 2/3。

### 路线 2：拿到 `.dat` 的 AES 固定密钥

继承图片那份逆向的进度（XOR 已破）。拿到 AES 密钥后，语音条若也走同一套 `.dat` 加密，
就能解出 SILK/AMR 再转写。

- 成本：**高**，且不保证成功（密钥可能是按账号/设备派生的，不是固定值）。
- 证伪点：**先确认语音条到底有没有落成 `.dat`**——第 3 条显示 `Rec\` 全空，
  所以**得先有一条样本**才知道它是 `.dat`、是在别的目录、还是压根不落盘。
  **在拿到样本之前，连这条路的入口都看不见。**

### 路线 3：改 hook 加一个 `Decode_Voice` 路由并重编译

hook 跑在微信进程里，已经有 `Decode_Pic`（说明它能调到微信内部的解密/解码入口）。
理论上可以照葫芦画瓢加一个语音版：hook 拿到字节 → 转成 SILK/AMR/WAV → 交给 Python 转写。

- 成本：C++ 改动 + `MSBuild` 重编译 + 真机验证。**风险已知**：CLAUDE.md 明确写了
  「编译产物和线上那个不是同一个二进制」，新 DLL 部署前必须先验证发消息等现有功能正常。
- 证伪点：微信内部有没有可复用的「取语音字节」函数（要读 hook 源码 + `Weixin.dll` 偏移）。

## 三、明确不做的事

- **不为了这条路去解密 `.dat` / 不重编译 hook**：在路线 1 没有结论、且**连一条语音条样本都没有**之前，
  这两件事都是纯赌博。CLAUDE.md 也写着「别顺手去解密 `.dat`」。
- 不把「以后也许能做」写成「支持语音条」——**当前的状态就是：做不到。**

## 四、下一步（要用户配合的那一步）

**先攒一条语音条样本**，然后一次把这些查清楚：

1. 用户在任意聊天里**发一条语音**（或让朋友发一条）；
2. 我停 bot，查：`fts` 里 `local_type=34` 的行长什么样、`Msg_` 那一行的
   `source` / `compress_content` / `packed_info_data` 是什么；
3. 用户**长按那条语音 → 转文字**；
4. 我再查同一行，对比有没有变化（路线 1 的证伪点）；
5. 同时全盘找新增文件（看有没有新的 `.dat`/`.silk` 落在 `Rec\` 或别处）。

只有第 2~5 步跑完，才能说清「语音条能不能读」；在那之前，任何实现都是在猜。
