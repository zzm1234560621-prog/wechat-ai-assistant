# 微信语音条 → 文字：可行性评估

## ★★ 2026-10-03：**能读了，而且有两条路**（先读这一节）

### 路 A（推荐，零成本）：微信自己的「转文字」**会落库**

真机取证：文件传输助手一条自己发的 1.24 秒语音（`local_id=613`），
在微信里右键 → 点一次「转文字」，然后对比那一行：

```
转文字前  Msg_9e20f478899dc29eb19741386f9343c8.packed_info_data = 080410385800
转文字后                                                          = 080410382A0D08021209E4BDA0E5A5BDE380825800
                      顶层字段: 1=4  2=56  5={<13 字节>}  11=0
                      字段 5 里: 1=2  2="你好。"      ← 转写结果就在这儿
```

也就是 **protobuf：`packed_info_data` → 字段 5 → 字段 2 = UTF-8 文本**。
同时 `download_status` 从 1 变成 5；`SessionTable` 和 fts **一个字都没变**。

**代价**：用户得在微信里**点一次**「转文字」（目前没法程序化触发）。
**好处**：零上传、零本地算力、零等待 —— 只要读那一列。

实现：`live_history.voice_transcript()` + `_render_nontext(34, …, packed)`
→ 渲染成 `[语音 1"] 你好。`；没转过则如实说「读不到内容，在微信里点一次转文字」。

顺带修掉一个**收不到语音**的真 bug：`_v4_pickup_nontext` 原来用
「`summary` 为空」当「非文本」的判据 —— 而**语音的 summary 是时长**（`1"`），
所以语音/表情/视频/系统消息**永远进不来**。现在判据改成结构性的
`last_msg_type NOT IN (1, 49)`（1 和 49 由 fts 覆盖）。

### 路 B（兜底）：微信进程**内存**里有明文 SILK

音频确实不落盘（见下），但微信要播它就得持有它 —— 实测在 `Weixin.exe` 内存里
搜到 60~145 处 `#!SILK_V3`，**都是明文 SILK**（紧跟 uint16 帧长，不用 aeskey）。
`ReadProcessMemory` 只读扫一遍（632MB 约 1~5 秒）→ `pilk` 解 SILK → 本地 whisper 转写。

**边界（实测，2026-10-03）**：
* 内存**能留住多久，和语音从哪来有关**，别一概而论：
  * 自己发的那条 1.24 秒语音（`local_id=613`）：20 分钟后**认不出**了 ——
    同长度站着 12 条别人的语音，时长匹配分不出来；
  * **手机发来的**那条 2.38 秒语音（`local_id=614`）：**30 多分钟后照样唯一命中**，
    转出「你好啊」（用户确认过就是这句）。
  所以结论是「**趁热更可靠**」，不是「必须趁热」；轮询 5 秒一次天然就是趁热的。
* 匹配靠**时长**（XML 的 `voicelength`）+ SILK 长度（XML 的 `length`）。
  趁热时通常只剩 **1 条**候选；晚了会撞上一堆同长度的，那时**不许替用户挑**；
  ⚠️ **2026-10-03 晚更正与细化见 `docs/voice-reliability-2026-10-03.md`**：真正能
  "唯一锁定"的信号是 **`length` 与那条 SILK 真实长度的精确对应（差 −1）**；
  而且"没有候补"里有一大半根本是**判据算错**（`est` 比真实帧数大 1~2 帧就当场放弃），
  不是内存里没有。
* 裁剪必须**按时长二分定位**（`voice_mem.silk_for_duration`）：
  按块结构裁会喂进垃圾刷 `SKP_Silk_SDK_Decode returned -12`，
  按「到下一个 magic 的距离」裁会把一条语音切成 0.02 秒的碎包
  （那条 1.24 秒的语音就是这么"消失"过一次）；
* **实测量级**：手机发来的语音，从"到达"到"出文字" **7.5 秒**
  （扫内存 1.2s + 解码 + 本地转写 ~5s）；机器忙时会飘到 14 秒。
  接进 bot 后这一段是**同步**的（跑在收消息那条线程上），见 `voice.auto_read`。

工具：`voice_mem.py`（模块）+ `_audit/{scan_weixin_memory_for_silk,
extract_voice_from_memory,rank_voice_candidates,bench_voice_read}.py`。

### 顺带修的真 bug：`pilk` 两代 API

`voice_msg.to_pcm` 只认老版 `pilk.silk_to_pcm2`，而 `pip install pilk` 现在装到的是
0.2.4（`decode(src,dst)` / `silk_to_wav(src,dst)`）→ **装了解码器也一条都解不出来**。
已改成两代都认（新版解出来是 24kHz，不是 16k，别默认采样率）。

### 音频为什么不落盘（2026-10-03 又翻了一遍，比上一版更全）

| 翻过的地方 | 结果 |
|---|---|
| `msg\attach\<md5(会话)>\<月>\{Rec,Img}\`（按 1812±256 字节找） | 命中全是明文富文本 / 图片缩略图 |
| **`cache\<月>\Message\<md5(会话)>\`**（上一版**漏了**这里） | 只有 `Bubble` / `Thumb` / `ImageTemp` / `SendTemp` |
| 20 个 **`VoiceTemp`** 目录 | 只有 2 个文件，且都是 **0 字节** |
| 整个 `cache` 树按 1812±64 找 | 命中的是表情 / 朋友圈图 / 聊天缩略图 |

> 另：`voice_msg.candidate_dirs()` 只扫 `msg\attach` 和 `msg\file`，**不扫 `cache\`** ——
> 按大小找载荷时记得把它算进去。

## ★ 修正：前一版错在哪、现在的判断是什么

| 前一版说的 | 实际 | 错在哪 |
|---|---|---|
| 「82 个 `Rec\` 目录**全是空的**」 | `Rec` 下**递归**有 **20415 个文件** | 只数了 `os.listdir` 的**顶层条目**，没递归。子目录 `Rec\<哈希>\Dat\0\<md5>` 里躺着内容 |
| 「最近 1.6 万条消息里语音 **0 条**」 | 语音**确实有**（两个群里抓到多条） | 只在 **fts** 里找 `local_type=34`。**语音和图片一样不进 fts** → 那条路是结构性盲的。必须查 `Msg_` 表 |
| 「拿不到音频字节，要破 AES 固定密钥」 | **不需要破全局密钥**：语音消息的 XML **自带 `aeskey`** | 没看语音的 `message_content` 就先下了结论 |
| 「`Rec` 里有语音」 | `Rec` 里那些文件是**明文 XML**（`<p><b>…`，富文本/appmsg） | 把目录名当成了内容类型 |

**现在的真实状态**：

1. **语音条在 `Msg_` 表里**（`local_type=34`），`message_content` 是 zstd 压缩的十六进制；
   解出来是 `<voicemsg voiceformat="4" voicelength="10880" length="20934"
   aeskey="…32hex…" voiceurl="…" fromusername="…" />`。
   → **`aeskey`（16 字节）就在消息里**，和图片一个套路。
2. **音频本体不在这台机器的磁盘上**：搜遍全盘**没有任何 size≈`length`(20934) 的候选音频**，
   那两个有语音的群 `Rec\` 是空的。
   → 最合理的解释：**微信按需下载**（不点开播放就不落盘）。
3. 工具链已经写好：`voice_msg.py`（解析 XML / 拿 key / 试解密 / 认 SILK·AMR 魔数 /
   交给 pilk·PyAV 解码）+ 观测器 `probe_voice.py`，回归在 `selftest_voice_msg.py`。
   ⚠️ 已实测到一个反直觉点：**魔数只能证明「第一块」解对了，分不出 ECB/CBC**
   （CBC 零 IV 的首块与 ECB 完全相同），所以 `identify()` 返回**候选列表**，
   真正的裁决是「哪个候选能完整解码出 PCM」。

**下一步（就差这一步）**：**去微信里点开播放一条语音条**，然后跑
`python probe_voice.py --tag after`。有新文件落地 → 用那条消息的 `aeskey` 试解 →
魔数对上 SILK → pilk 解码 → 交给已经做好的 `audio_read`（faster-whisper）转文字。

## 二、三条候选路线（按性价比排序）

### 路线 1：微信自带的「转文字」会不会落库（唯一可能零逆向的捷径）★先做这个

微信长按语音条有「转文字」。如果结果被写进 DB（`source` 列或别的字段），那我们**只要读它**，
不需要任何逆向——代价是用户得先长按转一次（体验差，但能立刻验证「到底有没有这条路」）。

- **验法**（需要用户配合，见第四节）：找一条语音条，**转文字前后**各查一次那一行，
  对比 `source` / `compress_content` / `packed_info_data` / `SessionTable.summary`。
- 证伪点：如果前后**一个字节都没变**，说明转文字只在内存里、不落库 → 这条路断，转路线 2/3。

### 路线 2：拿到 `.dat` 的 AES 固定密钥

继承图片那份逆向的进度（XOR 已破）。拿到 AES 密钥后，语音条若也走同一套 `.dat` 加密，
就能解出 SILK/AMR 再转写。

- 成本：**高**，且不保证成功（密钥可能是按账号/设备派生的，不是固定值）。
- 证伪点：**先确认语音条到底有没有落成 `.dat`**——第 3 条显示 `Rec\` 全空，
  所以**得先有一条样本**才知道它是 `.dat`、是在别的目录、还是压根不落盘。
  **在拿到样本之前，连这条路的入口都看不见。**

### 路线 3：改 hook 加一个 `Decode_Voice` 路由并重编译

hook 跑在微信进程里，已经有 `Decode_Pic`（说明它能调到微信内部的解密/解码入口）。
理论上可以照葫芦画瓢加一个语音版：hook 拿到字节 → 转成 SILK/AMR/WAV → 交给 Python 转写。

- 成本：C++ 改动 + `MSBuild` 重编译 + 真机验证。**风险已知**：CLAUDE.md 明确写了
  「编译产物和线上那个不是同一个二进制」，新 DLL 部署前必须先验证发消息等现有功能正常。
- 证伪点：微信内部有没有可复用的「取语音字节」函数（要读 hook 源码 + `Weixin.dll` 偏移）。

## 三、明确不做的事

- **不为了这条路去解密 `.dat` / 不重编译 hook**：在路线 1 没有结论、且**连一条语音条样本都没有**之前，
  这两件事都是纯赌博。CLAUDE.md 也写着「别顺手去解密 `.dat`」。
- 不把「以后也许能做」写成「支持语音条」——**当前的状态就是：做不到。**

## 四、下一步（要用户配合的那一步）

**先攒一条语音条样本**，然后一次把这些查清楚：

1. 用户在任意聊天里**发一条语音**（或让朋友发一条）；
2. 我停 bot，查：`fts` 里 `local_type=34` 的行长什么样、`Msg_` 那一行的
   `source` / `compress_content` / `packed_info_data` 是什么；
3. 用户**长按那条语音 → 转文字**；
4. 我再查同一行，对比有没有变化（路线 1 的证伪点）；
5. 同时全盘找新增文件（看有没有新的 `.dat`/`.silk` 落在 `Rec\` 或别处）。

只有第 2~5 步跑完，才能说清「语音条能不能读」；在那之前，任何实现都是在猜。
