# 语音条可靠性：根因、修法与真机证据（2026-10-03 晚）

> 本文是 `CLAUDE.md` 的 `audio_read.py` / `voice_mem.py` 段的细节延伸。
> 起因：语音条「短句稳、长句不行」——1.5 秒常能命中、3.5 秒撞车拒答、7.2 秒报
> 「没有一条时长接近」。
> **结论：原以为要换"唯一标识"，侦察后发现问题根本不在"找不到"，而在一个
> 3 行的估算闸把内存里明明完整的候选当场扔掉。已修，并补上 `length` 指纹。**

## 一、先纠正一个流传的说法：不是"长句内存里没有"

真机 `bot.log` 里 4 次「内存里搜到 SILK，但没有一条时长接近 X 毫秒」
（X = 3720 / 3400 / 4440 / **7180**），当时被解读成"长语音内存里留不住"。
**这个解读是错的。** 只读侦察（bot 停着）拿同一条 `local_id=690`（7180ms）实测：

| | 值 |
|---|---|
| 消息 XML 的 `voicelength` | **7180 ms** |
| 内存里那条 SILK 的真实帧数 | **357 帧 = 7140 ms**（真解码验证过） |
| 真实长度 | **12529 B** |
| 消息 XML 的 `length` | **12530 B**（= 真实长度 + 1） |

音频**完整地躺在内存里**，只比微信自己报的时长短 40 毫秒。

## 二、根因：`silk_for_duration` 的帧数估算闸（8/8 命中）

`voice_mem.silk_for_duration` 旧代码：

```python
est = max(1, int(round(float(target_ms) / FRAME_MS)))   # FRAME_MS = 20
if est > len(ends):
    return b"", float(len(ends) * FRAME_MS), "帧数不够，到不了目标时长"   # ← 当场扔掉
```

微信报的 `voicelength` **比真实音频长 20~40 毫秒**（侦察 8/8 都如此），
而 `est = round(voicelength / 20)` ⇒ `est` 比真实帧数**大 1~2 帧** ⇒
`est > len(ends)` 成立 ⇒ 真候选在**解码之前**就被丢掉。8 条真机语音全部如此：

| local_id | voicelength | 真实音频 | est | 真实帧数 | 旧代码 |
|---|---|---|---|---|---|
| 699 | 5580 | 8654B / 5560ms | 279 | 278 | ❌ 扔掉 |
| 698 | 2780 | 4440B / 2760ms | 139 | 138 | ❌ 扔掉 |
| 697 | 2480 | 3670B / 2440ms | 124 | 122 | ❌ 扔掉 |
| 696 | 1820 | 2924B / 1800ms | 91 | 90 | ❌ 扔掉 |
| 694 | 6860 | 10639B / 6820ms | 343 | 341 | ❌ 扔掉 |
| 690 | 7180 | 12529B / 7140ms | 359 | 357 | ❌ 扔掉 |
| 687 | 3800 | 6414B / 3780ms | 190 | 189 | ❌ 扔掉 |
| 685 | 4540 | 7724B / 4520ms | 227 | 226 | ❌ 扔掉 |

**修法（F1）**：`est` **夹到末帧**，不再直接放弃；"是不是这条"改由**实测时长**判定。
一条不变量没被放松：够不上目标时 `tol_ms` 照样拒答，所以**不是**把闸门拆了，
而是把拒答的依据从"估算帧数"换成"实测时长"。

⚠️ **顺手必须加"便宜闸"**（踩过才想到）：clamp 之后，以前不进解码的短 blob
会逐个去探测（每个最多 5 次 pilk 解码），长语音那一轮就是几百次解码 ——
这个函数同步跑在**收消息那条线程**上（真机卡死 4 次的那个坑）。
所以先按 `帧数 × 20ms + tol_ms < 目标` **不解码就判死**（这是精确判据：
SILK 每帧恒 20ms，任何前缀都不会超过它）。真机实测逐条判定 **0.06~0.46 秒**。

## 三、F2：消息自带的 `length` 才是那个"唯一标识"

原计划是用 `clientmsgid` / `aeskey` / `voiceurl` 在内存里**就近定位**。
侦察否掉了它（Q2）：这些标识在内存里各有 **5~10 处**、指向 **5~6 个不同 SILK**
（消息越新副本越多）；`voicemd5` 真机上**恒为空串**。

但同一份侦察露出一个更强的信号，而且**不需要内存锚点**：

```
消息 XML 的 length（加密字节数）  ←→  内存里那条 SILK 的真实长度（裁到帧边界）
        8/8 精确 = 真实长度 + 1
```

而**按时长**挑出来的候选差 **200~1900 字节**，转出来的明显是**更早的别的语音**
（`'帮我看一下'`、`'我跟了Superpoi你已經聊了'` 这些在当天 17:4x / 19:5x 的旧日志里出现过）。
`local_id=693` 那条还有**两条独立方法互相印证**：锚点（距离 132B）与 `length−1`
都指向 4373B / 2880ms。

管线其实**早就接好了**：`voice_msg.parse_voicemsg` 一直解析 `length_bytes`，
`live_history.voice_info` 一直返回它，`bot.read_voice_message` 只是**没往下传**。
所以 F2 的改动是：`voice_mem.read(..., target_bytes=...)`，**有候选命中指纹就用它，
一个都没命中就完全退回原来的时长逻辑**。

⚠️ **只当优先信号，绝不当硬门槛**：`−1` 这个关系只在**自己发出的**样本上验证过；
别人发来的语音走的是加密载荷长度，语义可能不同（2026-10-03 那条 2.38 秒的手机语音
就是唯一命中得很好的 incoming 样本）。当硬门槛会把 incoming 一条不剩地判死。

## 五、修不了的部分（也要如实说）

* **音频已经不在内存**：4/12 条（700 / 693 / 692 / 683）。两遍侦察之间内存里的
  SILK 从 **148 处掉到 99 处再到 85 处**，`693` 第一遍还在、第二遍就没了。
  这部分任何定位方法都救不了 —— **"读不出来就如实说"这条铁律必须留着**。
* **同一时长、同一字节数的两条不同语音**：指纹也分不开，那时仍走
  "置信度差得不够就拒答"。指纹是**减少**撞车，不是消灭。

## 五之二、修完之后**生产上又暴露的第二个失败原因**：8 秒预算太紧

修好 F1/F2 之后重启 bot，真机立刻又失败 3 条，其中 **2 条是「扫微信内存超过 8 秒
还没扫完，放弃了」** —— 这条超时在**此前整份 bot.log 里从未出现过**（0 次）。
一查，问题不在代码：

**实测（2026-10-03 晚，同一台机器、只读进程内存、bot 跑着也安全）：**

| 扫法 | 扫的字节 | 用时 | SILK 命中 |
|---|---|---|---|
| 现有判据（含只读区 / 镜像） | 1071MB | **4.0 / 4.9 / 16.0 s**（抖动极大） | 94 |
| 只扫私有内存（`Type=PRIVATE`，连测 3 次） | 430MB | **2.1 / 2.3 / 2.0 s**（很稳） | 91 |

两条关键结论：

1. **耗时与"扫了多少字节"不成比例**：1071MB 用 4.0 秒，430MB 要 2.1 秒，
   而 758MB（去掉只读区）反而要 **11.1 秒**。时间主要花在**冷页缺页**上
   —— 微信被换出去的页，读它要等磁盘。所以按"缩小范围"来提速**不可靠**。
2. 只扫私有内存确实又快又稳（2 秒），但会**丢掉 3/94 处命中**（其中 2 处在镜像页里，
   那更可能是 DLL 自带静态数据而不是用户语音；另 1 处是私有区，疑似抖动）。
   **没有采用**：为了 2 秒把它换成"可能少读一条真语音"不划算。

**改法**：把 `voice.scan_seconds` 默认 **8 → 20**（代码默认 + 两份 config 一起改，
注释里写清实测数字和代价）。代价要在文档里说清楚：最坏情况下这条语音让**轮询停
~20 秒**（再加转写 5~8 秒），期间消息**不丢**、排队回来照收；嫌停太久就调小或
`voice.auto_read: false`。
回归：`selftest_voice_msg.t8` 加了"默认预算 ≥ 实测上界 16 秒"的断言（防改回 8）。

⚠️ **仍未解决的一条**（下一节）以及一个**待验**的边界：`length` 指纹只在**自己发出的**
语音上验过；别人发来的（incoming）没验过，所以 `voice_mem` 里它只当"优先信号"、
不当硬门槛。侦察脚本 `_audit/probe_voice_incoming.py` 已写好，但**必须先停 bot** 才能跑。
在跑出结论之前，文档只写"未验证"，**不许**写成"通用"。

## 五之三、8 秒改成 20 秒之后仍可能失败的那条：`voicelength` 差得更大的语音

同一批里还有 1 条失败是 `没有一条时长接近 8340 毫秒`（不是超时）。它有两种可能，
**本轮还没能区分**（区分它需要停 bot 查那条消息的 `length` + 扫内存）：

* **(a) 音频不在内存**（那条语音已存在 30 分钟以上，内存换出）⇒ 无解，如实说；
* **(b) 音频在，但 `voicelength` 比真实音频长 **超过 60ms****：F1 修的是"差 20~40ms
  被误杀"，容差仍是 `SILK_TOL_MS = 60`；**而且 F2 的指纹救不了它** ——
  `candidates()` 里 `bytes_delta` 只对**已经通过时长闸**的候选计算，
  时长闸先拒掉的 blob 根本轮不到指纹说话。真机 8 个样本的差是 20/40ms，
  样本里没出现过更大的差，所以 (b) 是**推测**，不是结论。

⇒ 要判定 (b)，需要的改法是"**指纹命中就允许放宽时长闸**"（例如字节精确命中 ±2 时，
时长容差放到 300ms 再校验），但**先量、再改**：拿那条 8340ms 消息的真实 `length`
去内存里找，看有没有一条 blob 的帧边界长度正好等于它。有 ⇒ (b) 成立、值得改；
没有 ⇒ (a)，什么都不用改。

## 六、⚠️ 别改回去什么

1. `est` 那个 `if est > len(ends): return …` **不许加回来** —— 它是"长语音一条都
   读不出来"的根因（真机 8/8）。
2. `total_ms + tol_ms < target` 这个**不解码就判死**的便宜闸**不许删** ——
   删了就是几百次 pilk 解码同步卡在收消息线程上。
3. `target_bytes` 的指纹**只许当优先信号**，不许改成硬过滤 —— 会把 incoming 判死。
4. **免费路（微信自带「转文字」）本来就接好了**，见下面第七节的纠正。

## 七、纠正：免费路并没有"缺口"（原记录说错了）

`docs/voice-notes-2026-10-03.md` 里那节「还没做的一件事（已知缺口）」说
"英文界面拿不到微信自己转好的文字，因为 `_VOICE_TAG_RE` 不认 `[Audio]`"。
**这个判断不成立**，两处读码结论：

1. **正常轮询路径已经带着 `packed_info_data`**：`_v4_pickup_nontext`
   → `_v4_history_from_tables`（`live_history.py:790`，SELECT 里就有 `packed_info_data`，
   第 864 行传给 `_render_nontext`）。语音不走 fts（结构性事实），走的正是这条路。
2. **有转写时渲染出来的标签是我们自己的中文 `[语音 …]`**
   （`_render_nontext`：`return f"[语音 {s}] {txt}"`），**跟微信界面语言无关** ——
   所以 `_VOICE_TAG_RE` 认得出，英文界面一样能拿。
3. `voice_already_transcribed` 的调用点在 `bot.py:2881`，**外面前置了
   `local_type == 34`**，所以"用户手打 `[Audio] …` 被当成已转写"这条路
   本来就走不通 —— 那条顾虑在调用方已经用**结构**挡住了。

**真正剩下的**是另一处（罕见）缺口：最后一道兜底 `_v4_new_messages_session`
（fts 与 Msg_ 表**同时**掉线时才走）只读 `SessionTable`，产出的消息
**没有 `local_type`**，内容是微信的 summary 原文 —— 英文界面下就是日志里那条
`[Audio] 8"`。它没有 `local_type`，所以语音分支进不去、被当"只有类型标签"跳过。

### ✅ 已修（2026-10-03 晚，用户批准后）

`_v4_new_messages_session` 的 SELECT 补上 `SessionTable.last_msg_type`，并把它原样
带进产出的消息（和 `_v4_pickup_nontext` 同一套代码空间 —— 那边就是用
`last_msg_type NOT IN (1, 49)` 判非文本的）。三种结果：

| 情形 | 改之前 | 改之后 |
|---|---|---|
| 英文界面语音（summary `[Audio] 8"`） | 被当"只有类型标签"**静默丢掉**，连失败提示都没有 | 进语音分支 → 如实回「这条语音没带 local_id，认不出是哪一条」 |
| 中文界面语音（summary `1"`） | 更糟：**`1"` 被当成用户说的话送进模型** | 同上，如实回一句 |
| 取不到 `last_msg_type`（老库/结构变了） | —— | **不加这个键**，行为与以前一字不差 |

⚠️ 代价要记住：这条路**拿不到 `local_id`**（它按设计不碰 `Msg_` 表），所以它只能把
"静默丢掉"变成"有话说"，**不会真的读出语音内容**。别把它当成"语音在这条路上也能读了"。

回归：`selftest_live_history`（兜底路带 `local_type=34` / 文本带 1 / 取不到时**不加键**）。
下游那一半（`local_type=34` 且没带 `local_id` → 如实说）由
`selftest_aixed` 已有的用例钉着。

## 六、另一条硬边界：**微信必须是普通权限（Medium）跑的**（2026-10-06 真机）

### 症状

用户连发两条语音，每条都收到：

```
🎤 收到一条语音，但没能读出来：读不到微信进程内存（微信没在跑？或者权限不够）。
```

而**微信明明在跑**，bot 自己还在正常收消息、正常回话（`bot.log` 里轮询心跳不断）。

### 根因（已取证，不是猜）

`voice_mem.weixin_main_process()` 里那句 `OpenProcess(QUERY_INFORMATION|VM_READ)`
被系统拒绝：**微信进程以 High 完整性级别在跑**（提权打开的），而助手是 Medium。
跨完整性级别时 Windows 不允许低权限进程拿高权限进程的 `VM_READ`（`err=5`）。

真机实测（2026-10-06，同一台机器、同一时刻）：

| 探针 | `OpenProcess` | token 完整性级别 |
|---|---|---|
| 普通权限 python | ❌ 全部 5 个 `Weixin.exe` 都 `DENIED err=5` | —（连 `OpenProcessToken` 都是 err=5） |
| **提权** python | ✅ 5 个全部 `OK` | 自身 `0x3000 High`、**Weixin `0x3000 High`** |
| 对照 explorer | — | `0x2000 Medium` |

顺手能解释"为什么只有语音坏、别的都正常"：hook 的数据库查询走 **HTTP**（不是内存），
所以消息、历史、发消息全都不受影响，只有需要**读微信进程内存**的语音条这一条链断掉。

### 修（对用户）

1. **关掉微信，从开始菜单普通双击重开**（推荐；助手不用动）。
   之后 `_audit\check_voice_ready.py` 应当打印 ✅。
2. 或者反过来：让**助手也以管理员身份运行**（代价更大，别默认这么干）。

### 代码侧改了什么

失败文案以前把两种情况混成一句（"微信没在跑？或者权限不够"），把用户往
"微信开没开"这个**反方向**引。现在 `weixin_main_process(probe=ProcessProbe())`
把两件事分开记（`saw_any` / `denied`），`voice_mem.read()` 据此说三句不同的人话：

| 实情 | 文案 |
|---|---|
| 进程表里没有 `Weixin.exe` | 「进程表里没有 Weixin.exe —— 微信**没在跑**」 |
| 有 `Weixin.exe`、一个都打不开 | 「读到微信进程了，但**打不开它的内存**……**不是「微信没在跑」**」，并给出上面那两条路 |
| 有进程、句柄也有、但没有带 `Weixin.dll` 的 | 单独一句（微信在启动中 / 被安全软件拦） |

`weixin_main_process()` 的**返回值契约不变**（仍是 `(pid, handle)`），
所以老调用方和旧自测都不受影响；诊断只走新增的可选 `probe=` 参数。

零代价自检（不扫内存、不查库、bot 开着也能跑，**要和助手同权限跑**）：

```bash
.venv\Scripts\python.exe _audit\check_voice_ready.py
```

回归：`selftest_voice_msg.t11_memory_access_message`（三档文案 + 契约 + 不传 probe 照旧）。

⚠️ 别退回"进程存在就一定有句柄"的写法：这条链的**权限前提**是硬边界，
判断不出来的时候要如实说，不许拿旧文案糊过去（用户会照错误方向排查）。
